## 6. 压测形态判定与参数辨析（案头必备）


### 6.1 三种压测形态：A / B / C


| 形态 | 发送时机 | 行为 | 测出什么 |
|---|---|---|---|
| A. Worker 池（闭环） | 某个 worker 的请求返回后才发下一个 | N 个并发永远在飞，“看起来同时” | 吞吐上限 λ_sat（合法用途仅限于此） |
| B. 一次性齐射（burst） | t=0 全部打出 | 瞬间 ρ≫1 再泄洪 | 泄洪时间/最大承压，无稳态 |
| C. 预定时刻表（开环） | 按泊松过程预定时刻发，不管前面回来没有 | 真实到达过程，队列真实形成 | 给定 λ 下的 P50/P90/P95（含排队） |

**组合规则：rate 管”想多快”，concurrency 管”让多快”——闸门比想法硬。** --request-rate inf（想齐射）+ --max-concurrency 10（闸门）同时存在时：t=0 先齐射 10 个（B 开局），之后回一个补一个（A 续航）。样本主体运行在闭环 → **定性为 A**。

**并发有三层，闭环压测只控第一层**：

1. **客户端并发**：同时在"发请求等回复"的 worker 数（--max-concurrency 管这层）——请求可能还憋在客户端，根本没打到服务端；

2. **运行中并发**：调度器放进 GPU batch 正在算的请求数（num_requests_running）——受 token 预算和准入上限约束（见 4.6）；

3. **KV 槽位并发**：显存能同时容纳的 KV Cache 条数（c_kv，见 2.3/3.1）——物理硬顶。

闭环压测把第一层开到 100，不等于 GPU 在跑 100：可能只有二十几个在算，其余在客户端或 waiting 队列排队（三层的关系见 6.4、4.6）。**客户端视角的"并发"不是 GPU 视角的"并发"。**


### 6.2 十秒判定流程

看 bench 命令行：

├─ 有 --request-rate <有限值> ................ C 开环（唯一正确的测体验姿势）

├─ rate=inf 且 max-concurrency < 请求数 ...... A 闭环（开头带一波 B）

└─ rate=inf 且没设 max-concurrency .......... B 纯齐射


### 6.3 Coordinated Omission（协同遗漏）：闭环如何隐藏痛苦

例：服务端正常 100ms/请求，100 worker 闭环压（稳态 1000 QPS），60 秒内 t=30s 时服务端停摆 5 秒（KV swap、长 prefill 卡 batch）：

**开环（900 QPS 持续打）**：5 秒涌入 ~4500 请求全部排队 → P99 ≈ 4~5s（真相）。

**闭环（100 worker）**：停摆时 worker 全卡住，**无新请求产生**；恢复后补发的请求只体验 ~150ms。55000 样本中经历事故的只有 100 个（0.18%）→ 报告 P99 ≈ 150ms。

**同一次事故：开环报 5 秒，闭环报 150 毫秒。** 系统越慢闭环客户端发得越慢，负载节奏与系统难受时刻自动”协调”，恰好避开最该测的样本——痛苦不是不存在，是被客户端藏在了测量视野之外。


### 6.4 客户端 vs 服务端参数：两个 max 的搏斗


|  | --max-concurrency | --max-running-requests（SGLang）/ --max-num-seqs（vLLM） |
|---|---|---|
| 位置 | 客户端（bench 信号量） | 服务端（调度器准入上限） |
| 控制什么 | 下一个请求什么时候发 | batch 同时最多跑几条 |
| 超出的请求 | 憋在客户端，根本没发出 | 进服务端 waiting 队列，真实排队 |
| 排队可见性 | 没人看见（TTFT 从发送才计时） | 完整计入 TTFT，看得见 |
| 性质 | 闭环的元凶 | 生产必需的过载保护 |

**队列总是在最紧的闸口前形成。** 客户端闸口（如 32）比服务端（256）紧 → 服务端队列永远空，痛苦全在客户端视野外。

**三层对照表（背下来）：**


| 层 | SGLang | vLLM |
|---|---|---|
| 压测客户端（管”发不发”） | sglang.bench_serving --max-concurrency | vllm bench serve --max-concurrency |
| 推理服务端（管”跑不跑”） | launch_server --max-running-requests（默认自动推导） | vllm serve --max-num-seqs（默认 256） |
| 网关/路由层（隐藏款） | sglang_router --max-concurrent-requests（配 –queue-size） | 无内置（用外部网关） |

**口诀**：带 concurrency 的都是客户端（两家通用）；服务端 SGLang 叫 running、vLLM 叫 seqs。

**正确姿势”一留一去”**：留服务端准入（生产防线，压测时还能验证过载行为是排队还是雪崩）；去客户端闸门（或抬到 1024 当保险丝），换 --request-rate 开环。


### 6.5 开环压测 SOP（可直接照抄）

--request-rate 设有限值（vLLM 默认泊松到达），**不设** --max-concurrency；

从 0.3×λ_sat 起扫 5 档（0.3/0.5/0.7/0.85/0.95×λ_sat）；

每档样本 ≥500（P95/P99 才有统计意义），稳态时长 ≥10× 平均服务时间，剔除预热；

负载仿真真实：--random-range-ratio 0.5 引入长度方差，或直接用业务分布/ShareGPT（公开的真实对话数据集）；

报告 P50/P90/P95/P99，且 **TTFT、TPOT（即 ITL，逐 token 间隔）、E2E 分开报**；

口径铁律：TTFT / ITL 必须注明前缀缓存命中口径——带共享前缀的数据集测出的 TTFT 是"命中价"（同文档追问场景），全新文档冷启动首问是另一个价（可能差一个数量级）；两个数字都真实，但客户拿命中口径去验收冷启动，就是事故。

投机解码（MTP / SD）开启时，ITL 分位数口径失真——token 成簇到达，分位数落在簇内/簇间间隔的混合分布上，不再是干净的单步时钟；吞吐与 TTFT 口径不受影响。要核 ITL 点值，须抓引擎侧 step 时延与接受率指标。

同时抓服务端 num_requests_waiting、KV 占用率（指标名以所用框架版本为准）佐证；

画 λ vs P95 曲线，**拐点 ÷1.2~1.4 安全系数 = 生产可承诺容量**；

继续升 λ 压出故障模式：验证准入控制是”快速拒绝”还是”慢性死亡”。


### 6.6 多轮对话压测：单轮结果不能直接用于多轮业务

上面的 SOP 是单轮无状态负载。真实多轮业务有两个结构性差异：

**机制一：上下文随轮次膨胀，λ_sat 整体下移**。第 1 轮输入 2K，第 5 轮输入 10K（含历史）——单请求的 KV 占用和 Prefill 算力随轮次线性涨，三面墙全部收紧。同一台机器，单轮短输入的 λ_sat 与"平均 5 轮"业务的有效 λ_sat 可能差数倍。

**机制二：轮间有思考间隔，会话并发 ≠ 请求并发**。KV 在请求完成时释放，第 5 轮的大上下文只在第 5 轮执行期间占显存；1000 个在线会话同时处于"正在生成"状态的远少于 1000。容量仍按请求级 λ 算（口径见第 0 章）——既不要因为"会话多"而恐慌性加卡，也不要因为"单轮测得快"而乐观性减卡。

**折中压测方案（不用写会话状态机）**：按业务轮次分布构造"模拟轮次"的独立请求组，混合打流——


| 请求组 | 模拟 | 输入构成 | 混合比（示例） |
|---|---|---|---|
| A | 第 1 轮 | 2K（系统提示 + 首问） | 40% |
| B | 第 3 轮 | 6K（历史 + 新问） | 35% |
| C | 第 5 轮 | 10K（更长历史） | 25% |

两条铁律：① B/C 组的输入必须包含**真实重复前缀**（系统提示词、工具定义），随机生成的前缀会把前缀缓存命中率压成 0，测出的是悲观下界（见 3.6）；② 混合比用业务实测轮次分布，不要拍脑袋。

**可直接照抄**（配套脚本 构造多轮混合负载.py 生成混合数据集，再开环打流）：

```bash
# 1) 准备三组 prompt：prompt_2k.jsonl（首轮）/ prompt_6k.jsonl / prompt_10k.jsonl
#    6K/10K 组的历史部分用真实会话日志改写；系统提示词单独存 system_prompt.txt
# 2) 按轮次分布混合 5000 条，6K/10K 组自动拼共享前缀（激活前缀缓存）
python 构造多轮混合负载.py \
  --turn-dist "0.4:prompt_2k.jsonl,0.35:prompt_6k.jsonl,0.25:prompt_10k.jsonl" \
  --shared-prefix system_prompt.txt --n 5000 --out mixed.jsonl
# 3) 开环打流（同 6.5：不设 max-concurrency 或抬到 1024 当保险丝）
vllm bench serve --dataset-name custom --dataset-path mixed.jsonl \
  --request-rate 50 --num-prompts 5000
```

**结果使用**：混合负载测出的 λ_sat 直接进排队模型；报告注明轮次分布口径，换分布要重测。

**暗坑提醒：前缀缓存容量要按"会话"规划，不是按"请求"**。引擎按请求无状态——请求完成 KV 即释放，引擎不知道"会话"的存在；多轮历史靠前缀缓存承接，而前缀缓存是**可被挤出的隐式状态**：活跃会话数 × 平均会话上下文 超过前缀缓存可用空间时，最久未用的前缀被挤出 → 命中率崩塌、prefill 成本暴涨。所以多轮业务要额外核一笔账：**前缀缓存可用空间 ≥ 活跃会话数 × 平均会话上下文 ÷ 目标命中率**；不够就扩大显存配额，或接受命中率打折后的 λ_sat。若部署了 KV 分层卸载（外置 KV 池）或自研会话驻留，KV 墙直接按会话级重算：c = KV 池容量 ÷ 平均会话上下文。


### 6.7 测完怎么看数：SLO 容量 λ* 与物理上限 μ 是两笔钱

压测报告一出来，所有人都会问同一个问题："这台机器到底能出多少 token？"——这个问题有两个正确答案，混用必出事：


| 口径 | λ*（SLO 容量） | μ（物理上限） |
|---|---|---|
| 定义 | SLO 全达标的最大到达率 | 不管体验硬挤出的最大吞吐 |
| 体验前提 | P90/P95 全部达标 | 尾延迟已破线，队列持续积压 |
| 适用业务 | 交互式：对话、问答 | 跑批、离线：夜间批量任务 |
| 能否对客户承诺 | 唯一能承诺的数 | 只能写"≥"，且必须注明口径 |

判读 μ 有没有到头，看爬坡曲线的斜率：**真到顶的相 = 到达率翻倍、吞吐不动、失败率抬头，三者同时出现**。曲线还在涨（哪怕亚线性）只说明一件事：测试档位用完了，不是机器到顶了。实测：某 64 卡国产 PD 分离集群开环爬坡，0.4→0.8 QPS 吞吐仍 +34%（1059→1422 tok/s）、零失败——报告只能写"μ ≥ 1422"，谁拍精确数字谁不诚实。

跑批的工时是算得出来的（工单制）：跑批和交互相反，开工前任务量全知道。**ETA ≈ 总输出 token ÷（μ × 0.7）**，0.7 是安全垫；装不下的单不接或拆两晚。跑批任务晚 10 小时交付，99% 的业务无所谓；交互客户等 10 秒就骂人——**可延迟的资产给不可延迟的资产让路，天经地义。**

为什么开环测出的 μ 经常比闭环高一截？三件事叠加：①闭环稳态吞吐被"人数 ÷ 单请求时长"封顶，请求完成的瞬间 decode 批次有空窗；②开环过载时等待队列深，引擎面前永远有活，decode 每轮满批次跑——MoE 模型批次越大，专家权重读一次摊给越多请求，单步吞吐越高；③若数据集带共享前缀，开环的 prefill 成本被缓存摊掉，省下的算力全让给 decode。所以"开环 1422 > 闭环 1114"不矛盾：**一个是限流下的稳态产能，一个是挤爆时的瞬时产能**——后者不可持续（队列无限长），但它标定了物理上限。

与 7.3 合看，闭环的账就齐了：**闭环既高估体验（协同遗漏藏起尾延迟），又低估产能（批次空窗压吞吐）**。两个方向的偏差同一个根源：闭环客户端的发送节奏被系统速度反向挟持。

口诀：给客户报价看 λ*，给跑批排班看 μ，两个数写进同一行就是给自己挖坑。


### 6.8 "你的流量是预设的，不真实"——标准回应

开环压测被质疑最多的一句话。三层回应，由硬到软：

第一，**预设的只是平均速率，到达时刻是真随机的**。泊松到达（vLLM 默认）是排队论模拟真实客流的标准模型——银行网点、医院挂号、呼叫中心的客流建模全用它。"预设"两个字只扣在速率刻度上，"随机来人"这件事本身是仿真的，不是理想化的整齐排队。

第二，**破线点是系统的属性，不是流量的属性**。排队论铁律：平均到达率持续超过服务率，队列必然无限增长——与流量形状无关。开环扫档干的事，是用递增压力把服务率边界"挤"出来。类比：拿消防水压测水管，爆了——你不能说"这水压是预设的、不真实"，爆管压力点是水管的属性。

第三，两个诚实边界要主动说，别等对方挑：①λ* 是**持续平均**口径——真实流量的短时尖峰靠队列吸收，所以 λ* 是保守承诺（平均低于它，体验有保障），不是"瞬时碰线就炸"；②λ* 按**标准请求**（特定输入/输出长度）标定——真实业务请求更短，等效容量更高，引用时必须做业务量折算。

兜底反问："拿猜测的流量形状测出来的数，反而没有容量边界的物理意义——您希望测系统属性，还是测我的想象力？"


### 6.9 Trace 回放：从"测系统脾气"到"验收具体客户"

合成压测（泊松开环 + 闭环）和真实日志回放不是谁替代谁，各管一件事：合成压测回答"**这台机器的脾气是什么**"（λ*、μ、瓶颈位置——系统属性，不随流量变）；trace 回放回答"**这个客户的生意，在这台机器上跑不跑得下来**"（具体验收）。

trace 回放把合成压测里的四个假设全部换成真值：①真实到达过程——真实客流多半比泊松更狠（早高峰、整点定时任务突发），λ* 是平均口径，trace 告诉你峰值口径下还达不达标；②真实请求长度分布——容量按真实混合重新折算；③真实会话结构——多轮对话、同文档反复追问的比例，决定前缀缓存的真实命中率，直接修正 TTFT 的命中口径（见 6.5 口径铁律）；④峰值/均值比——决定容量承诺要留多少安全垫。

找客户要 trace，**四个字段就够：请求时间戳、输入 token 数、输出 token 数、会话 ID**——只拿形状不碰内容，脱敏争议最小。回放跑三档：原速 1×（验收）、1.5×、2×（看余量）。

但记住 trace 的边界：**它只能验证"过去"**。客户业务涨三倍后什么样，还得回到 λ* 折算外推。所以两张牌都要：合成压测画能力地图，trace 回放做落地验收。

口诀：**合成定边界，回放做验收，外推靠边界。**
