## 3. 系统层：单节点 λ_sat 的正确推导


### 3.1 三面墙取最小

λ_sat = min( λ_compute, λ_tpot_sla, λ_kv )　（三项分别是算力墙、TPOT-SLA 墙、KV 槽位墙各自允许的 QPS 上限；TPOT_sla = SLA 承诺的逐 token 间隔上限）

墙1 算力墙：FLOPs/请求 = 2×N_active×(L_in+L_out)

λ_compute = n_gpu×F×MFU / FLOPs每请求

墙2 带宽墙：λ_tpot_sla = (BW_eff×TPOT_sla − 权重字节) / [ctx×kv_per_token×(TTFT_service + L_out×TPOT_sla)]

【kv_per_token 是什么】每个 token 的 KV 缓存字节数：模型每多记住一个 token，就要替它存一份 Key/Value 向量，这份向量多少字节由模型结构决定（层数 × KV 头数 × 每头维度 × 精度字节，推导见 2.3——GQA 70B 级 BF16 ≈320KB/token，MLA FP8 ≈35KB/token）。于是 ctx×kv_per_token = 一个请求每个 decode 步要重读的历史 KV 字节；墙 2 分母的整体读法 = 每步的 KV 胃口 × 每人占坑时长。

墙3 显存墙：λ_kv = c_kv / S          （S = TTFT_service + L_out×TPOT）

【口径防混：墙 3 的 S 和墙 2 的 S 不是同一个】墙 2 问的是"SLA 压线时能跑多快"——TPOT 取 SLA 上限（如 50ms），S 是压线口径的服务时长；墙 3 问的是"显存槽位实际周转多快"——S 必须取实际运行的服务时长（3.2 自洽解出来的那个，通常远小于压线值）。拿 SLA 口径的 S 代进 λ_kv = c_kv/S：S 偏小 → λ_kv 虚高 → 误判"显存墙不约束"，实际上槽位早就满了。两面墙各用各的 S，别串。

**最常见错误**：只用 Decode 吞吐 ÷ L_out 估算 QPS，假装 Prefill 免费。2048/512 负载下高估 ~4 倍（吞吐的三个口径见 2.5）。

**【人话】**单节点 QPS 天花板 ＝ 算力、带宽、显存三面墙里最矮的一面——木桶原理，另外两面再高也没用。

**【代入】**算例 A：min(8.6, 37.7, 193) ＝ 8.6 QPS。算力墙最矮，带宽墙余量再大也白搭。

**【直觉】**花钱之前先问"哪面墙最矮"；加高非最矮的墙，收益恒等于零。

**墙 2 公式拆开看（全手册压缩率最高的一行，三步推出来）：**

**第 1 步｜一个 decode 步搬多少：**权重 W（全 batch 共享，只扫一遍）＋ B×ctx×kv_per_token（每个请求的历史 KV 各算各的）。SLA 要求 (W ＋ B×ctx×kv_per_token) ÷ BW_eff ≤ TPOT_sla。

**第 2 步｜解出 SLA 容忍的最大并发：**B_max = (BW_eff×TPOT_sla − W) ÷ (ctx×kv_per_token)——每步搬运预算扣掉雷打不动的权重，剩余字节全给 KV 分，除以每请求每步的 KV 胃口。

**第 3 步｜并发上限换成 QPS 上限：**靠 Little 定律（B = λ×S）：λ_tpot_sla = B_max ÷ S，S = TTFT_service ＋ L_out×TPOT_sla（每人占坑多久）。

**【代入】**（算例 A）预算 16.1TB/s×0.05s ≈ 805GB，扣权重 72GB 剩 733GB；每请求每步 KV = 2304×320KB ≈ 0.74GB → B_max ≈ 990；S ≈ 0.1＋25.6 ≈ 25.7s → λ ≈ 38 QPS，与 3.3 的 λ_tpot_sla ≈ 37.7 一致。

**【MoE 专项】**“权重字节”在 Dense 下是真常数（每步必扫全量）；在 MoE 下随 batch 爬升——batch=1 时只扫激活专家（R1 仅 ≈37GB），规划工况的大 batch 下路由并集趋近全量（≈671GB），规划必须按饱和全量计。反面教训：拿 batch=1 的 37GB 做规划，等于又犯一次单流压测式自欺——权重搬运被低估 18 倍。MoE 稀疏的是计算，不是搬运。


**【直觉】**分子 = 每个 TPOT 周期搬完权重后还剩多少字节给 KV。SLA 每收紧一分，先挤死的是 KV 预算；分子变负 = 吞吐工况下不可行（不是单流跑不动，是 batch 一大就违约）。


### 3.2 自洽求解（闭式）

B=λS（Little 定律，即利特尔法则：在制请求数 = 到达率 × 平均服务时间）、S 依赖 TPOT、TPOT 依赖 B，消元得：

TPOT = (W + λ·ctx·k·T_f) / (BW_eff − λ·L_out·ctx·k)　（W = 权重字节数；ctx = 平均上下文 ≈ L_in+L_out/2；k = kv_per_token；T_f = 每请求固定开销（典型 3~15ms）；BW_eff = 有效带宽 = n_gpu×BW×MBU；B = 同时在生成的请求数，即 batch）

取 λ=λ_compute 代入即得 TPOT、S、B；再用墙 2、墙 3 封顶。

**【人话】**batch 越大 → 每个 token 越慢（TPOT 涨）、但每秒产的 token 越多——吞吐和延迟互相咬尾。这条公式把咬尾一次解开：给定 λ，直接算出稳态的 TPOT、S、B。

**【直觉】**不用背。记住链条就够：B 涨 → TPOT 涨、吞吐也涨，SLA 是刹车片；算不动时交给配套计算器。


### 3.3 算例 A：Qwen2.5-72B（FP8）× 8 卡 H100

输入：72B Dense，FP8 权重 72GB，KV FP16 320KB/token；L_in=2048，L_out=512；MFU=0.40，MBU=0.60，mem_util=0.90（待锚定）。

**第一步：闭式解算三面墙，取 min**

| 步骤 | 数值 |
|---|---|
| KV 池 = 8×80×0.9−72−10 ≈ 494GB | c_kv ≈ 151万token/2560 ≈ 589 槽位 |
| 有效算力 = 8×989×0.4 ≈ 3165 TFLOPS；单请求 3.69e14 FLOPs | λ_compute ≈ 8.6 QPS |
| BW_eff = 8×3.35×0.6 = 16.1 TB/s → 闭式解 | TPOT≈5.7ms，S≈3.0s，B≈26 |
| λ_tpot_sla ≈ 37.7；λ_kv ≈ 193 | 均 ≫ 8.6，算力墙约束 |
| λ_sat ≈ 8.6 QPS ≈ 4400 输出 tok/s | 与公开实测（TRT-LLM FP8 3~4.5k tok/s）吻合 |

**【KV 池这笔账怎么拆】**8×80 = 8 卡 H100 总显存 640GB；×0.9 = 引擎可用上限（mem_util，vLLM 惯例 gpu_memory_utilization=0.9，预留 10% 给激活峰值、CUDA Graph、显存碎片和驱动自身开销）；−72 = FP8 权重常驻显存；−10 = 通信 buffer 与工作区预留（与 0.9 已留的 10% 是双重保险，方向保守、安全）。

**顺流而下两笔：**151万 token = 494GB ÷ 320KB/token（每 token 的 KV 字节，2.3 的 kv_per_token 公式）；589 槽位 = 151万 ÷ 2560（每请求占用 L_in+L_out = 2048+512 个 token 的记忆）。全链条：显存 → 能装多少 token 的记忆 → 能同时服务几个人。

**【算例 A 剩余两格怎么拆】**单请求 3.69e14 FLOPs = 2×72B×(2048+512)（3.1 墙 1 公式代入）；λ_compute = 3165×10¹² ÷ 3.69×10¹⁴ ≈ 8.6 QPS。

**两堵非约束墙的来历：**λ_tpot_sla ≈ 37.7 = 墙 2 公式代入：50ms 预算下 16.1TB/s×0.05s = 805GB，扣权重 72GB 剩 733GB，÷ 每请求每步 KV（ctx 取 L_in+L_out/2 ≈ 2304 token × 320KB ≈ 0.74GB）≈ 990 并发（即 B_max），再 ÷ S_SLA（≈ 25.7s）≈ 38。**【S_SLA 是什么】**即墙 2 公式分母的括号项（TTFT_service + L_out×TPOT_sla）。TTFT_service ≈ 0.10s 分两笔：prefill 项 = 2×72B×2048 ≈ 2.95e14 FLOPs ÷ 3165 TFLOPS ≈ 0.093s（2.4 公式第一项）；固定开销取 ≈0.01s（每条请求的调度/通信/采样杂费，与长度无关；区间 3~50ms 此处取 10ms——要确数就用多档 TTFT 实测拟合截距反解，不靠估）。L_out×TPOT_sla = 512×0.05s = 25.6s，合计 ≈ 25.7s。固定开销即使取到 50ms 上限，S_SLA 也只动 0.15%——decode 项 25.6s 是绝对大头，这项不配纠结。990 是带宽预算下的并发上限（头数），÷ S_SLA 就是 Little 定律把并发换成 QPS；S 取压线值而非实际值 3.0s 的原因，见 3.1【口径防混】。λ_kv ≈ 193 = c_kv 589 ÷ S 3.0s。两堵墙都 ≫ 8.6，只是校验项——这就是"取 min"的现场。

【ctx 为啥是 L_in＋L_out/2 ≈ 2304】decode 时每步要重读的 KV 随生成变长：第 1 个 decode 步读 L_in=2048 个 token，最后一步读 L_in＋L_out=2560 个，中间线性爬坡，平均每步读 (2048＋2560)/2 = 2304。等差数列求平均 = 首末相加除 2，所以新生成的 512 个 token 的 KV 只算"半份"（L_out/2）——它们平均只活了一半 decode 过程。

**第二步：敏感性——结论其实是一个区间**

λ_compute 与 MFU 严格成正比，MFU 取区间两端：


| 真实 MFU | λ_sat | 对 254 台规划的影响 |
|---|---|---|
| 0.30（悲观） | ≈ 6.4 QPS | 需 ~340 台，多 1/3 预算 |
| 0.40（占位） | ≈ 8.6 QPS | 254 台 |
| 0.55（乐观） | ≈ 11.8 QPS | ~185 台，浪费 1/4 预算 |

结论差将近一倍——这就是常数不锚定的代价。**重要说明**：占位值算出 4400 tok/s 落在公开实测区间（3000~4500）内，只说明"量级对"，绝不等于"MFU=0.4 很准"——若真实 MFU 是 0.30，同样落在区间内。

**第三步：锚定后替换（正式报告必须走到这一步）**。实测 2~4 个 TTFT 锚点，用 SLOPE 反解出真实 MFU 后替换 0.40 重算。锚定后 λ_sat 误差收敛到 ±10~15%，此时才允许写成确数（并仍须标注"常数来源：实测锚定"）。

**对照错误算法**：Decode 峰值 18300 tok/s ÷ 512 ≈ 35 QPS —— 高估 4 倍。


### 3.4 算例 B：Qwen2.5-32B（BF16）× 8 卡 H20

有效算力 8×148×0.42 ≈ 497 TFLOPS → λ_compute ≈ 3.0 QPS；BW_eff ≈ 19.8 TB/s → TPOT≈3.5ms，S≈2.1s。**λ_sat ≈ 3.0 QPS**。H20 带宽快但算力只有 H100 的 1/7：Prefill 重的负载吃亏，短进长出的 Decode 型负载才是甜区。

**【算例 B 拆账】**λ_compute：单请求 FLOPs = 2×32B×(2048+512) ≈ 1.64×10¹⁴；497×10¹² ÷ 1.64×10¹⁴ ≈ 3.0 QPS（MFU=0.42 为待锚定占位值）。

**BW_eff 的来历：**8 卡 × 4TB/s × MBU 0.62 ≈ 19.8 TB/s（MBU = 带宽有效利用率，与 MFU 同级纪律：必须锚定）。

**TPOT 与 S：**decode 每步读权重 64GB（32B BF16）÷ 19.8TB/s ≈ 3.2ms，加 KV 读取零头 ≈ 3.5ms；S = TTFT_service（2048 prefill ≈ 1.31×10¹⁴ FLOP ÷ 497TFLOPS ≈ 0.26s）＋ 512×3.5ms ≈ 2.1s。

**KV 墙校验：**KV 池 = 8×96×0.9 − 64 − 10 ≈ 617GB → c_kv ≈ 617GB ÷ 320KB ÷ 2560 ≈ 735 槽位 → λ_kv = 735 ÷ 2.1 ≈ 350，远不约束。三面墙 min(3.0, …, 350) = 3.0——算力墙约束，与"H20 带宽快、算力弱"的选型结论互为印证。


### 3.5 负载画像决定选型


| 负载画像 | 瓶颈 | 选型 |
|---|---|---|
| 长进短出（RAG 检索增强生成/文档问答） | Prefill 算力 | 高算力卡（H100/910C）、P/D 分离、前缀缓存 |
| 短进长出（创作/Agent） | Decode 带宽+KV | 高带宽大显存卡（H20/H200） |
| 超长上下文（>32K） | KV 容量+注意力二次项 | GQA（分组查询注意力）/MLA 模型、FP8 KV |
| 高并发小请求（客服） | 调度开销+槽位 | 中小模型多副本 |
| MoE 大模型（R1/V3） | 显存（总参数）+EP（专家并行）通信 | 大显存节点+EP 拓扑；算力按激活参数估 |

**【2026-08 补充：一套部署打不了所有流量——serving profile 分型】**画像表解决的是“选什么卡”；前沿实践（LMSYS V4-Pro × H20，L3）已细化到“同一模型、分阶段配拓扑”：prefill、低延迟 decode、高吞吐 decode 三类负载各配一套 serving profile（服务配置）——prefill 池长文本上 PP4-CP8-TP8（4 段流水线才能吃满并行度），低延迟 decode 用 PP2-TP8（跨两机把权重摊薄、腾显存给 KV），高吞吐 decode 用 DP32-EP32（EP 组越大越能腾显存接并发，但跨机流量占比上升、单卡效率下降——效率档 DP16-EP16 与容量档 DP32-EP32 之间没有标准答案，SLO 落在哪，工作点就选在哪）。**切换点全部是测出来的**：PP2 还是 PP4 的分水岭在 128K 上下文（1M 时 PP4 的 TTFT 少 44.8%），没人能拍脑袋定。规划含义：画像表定方向，profile 定配置，切换点靠锚定。


### 3.6 进阶修正：前缀缓存、P/D 分离与跨节点通信

方法论定位：P/D 分离不是第四层，而是把三面墙拆成两组各算各的——P 池只撞算力墙，D 池只撞带宽墙和 KV 墙；λ_sat 从「单节点取 min」变成「两个池各自取 min，再按 λ_peak 配比」。排队层一字不改，每池独立 M/M/c。真正新增的只有两笔账：一张网络入场券（KV 传输，不满足即出局，见下文判据）和一份隐性成本（两个池的余量不能共享——这就是 7.1.2 分离反而费卡的根源）。所以判断分离值不值，用的还是 0.5 节三条纪律：瓶颈是不是「Prefill 抢 Decode」、拿什么换什么、幅度×占比够不够回本。

**前缀缓存的量化收益**。多轮对话 / 固定系统提示词场景，若前缀命中率 h，有效输入长度 L_in′ = L_in×(1−h)，λ_compute 近似放大 1/(1−h) 倍。多轮对话 h 常达 0.5~0.9——对长输入负载这是数倍 λ_sat 的差异：**规划必须按业务实测命中率修正；压测必须带重复前缀**（定长随机数据 h=0，又一种自欺欺人）。

**【h 的温度计：命中率怎么实测】vLLM（V1）/metrics 暴露 vllm:gpu_prefix_cache_queries（查询总数）与 vllm:gpu_prefix_cache_hits（命中数），h ≈ hits ÷ queries；老版本看服务端日志周期打印的 "Prefix cache hit rate"。SGLang 在日志/metrics 输出同类命中率（指标名随版本漂移，以实际输出为准）。两个口径别混：压测 B/C 组的 h 由脚本里的重复前缀构造（是"你设计的"），生产的 h 由 /metrics 读出（是"业务给的"）——规划用后者，前者只用于验证引擎行为。**

**P/D 分离的配比方法**。P 节点按算力配、D 节点按带宽+显存配，各自独立扩缩：

- P 节点单节点吞吐：λ_P = n×F×MFU / (2×N_active×L_in)
- D 节点单节点吞吐：λ_D = 1 / (L_out × TPOT_D)
- 配比：n_P = ⌈λ_peak / (λ_P×ρ)⌉，n_D = ⌈λ_peak / (λ_D×ρ)⌉　（λ_peak = 峰值 QPS = PAR×λ_avg，详见 4.4；n_P / n_D = P 池 / D 池各自所需节点数）
- KV 传输：每请求 P→D 搬运 L_in × kv_per_token 字节；串行口径计入 TTFT，但**实际可与流水线重叠**——P 节点算完立即接下一个 prefill，传输与 D 节点 decode 并行：传输时间 < D 节点单步 decode 时间时 TTFT 增量 ≈ 0，只按净暴露时间计（下例中 400G IB 的 12ms 通常被重叠掉，25GbE 的 0.19s 重叠不掉）
**【人话】**P 池按算力配机器、D 池按带宽＋显存配机器，各算各的台数再相加——λ_peak 是同一个，分的是谁来扛。

**【直觉】**分离的本质是"各买各的便宜卡＋互不抢"，代价是一笔 KV 快递费（网络入场券）：快递费超过省下的卡钱，就不分。

例：16K 输入、MLA 35KB/token → 每请求传输 ≈ 560MB；25GbE（≈3GB/s）需 ~0.19s，400G IB ≈ 12ms——**网络档次直接决定 P/D 分离是否划算**。判据：L_in/L_out 越大、前缀复用越低，分离收益越大；短进短出场景分离反而白加传输开销。

**TP（张量并行：把每一层矩阵切开分摊到多卡）跨节点的通信墙。节点内 NVLink（GPU 间高速直连总线，~900GB/s）与跨节点 IB（InfiniBand 高速网络，400Gbps ≈ 50GB/s）差近 20 倍；TP all-reduce（多卡各自算完后汇总同步的集合通信）每层两次，通信量 ∝ hidden×B。判据：单节点放得下就不要跨节点 TP；必须跨节点时，通信占单步时间 >20% 就改 PP 或加节点降 TP 度。671B 级模型跨多节点 TP 效率远低于节点内——MoE 模型的等效效率里，有相当一部分就是这笔通信账。**
