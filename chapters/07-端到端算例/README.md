## 7. 端到端七步流程与完整算例


### 7.0 两种起点：从零规划 vs 存量纠偏

七步流程对两种情况通用，**分叉点只有一个：需求侧常数从哪来**。供给侧常数（单机服务能力 λ_sat、效率常数、KV 显存墙）由硬件和模型决定，两种情况都靠压测锚定，与有没有流量无关；分叉的是需求侧——请求量、峰值系数（峰值流量÷平均流量）、长度分布、到达/服务的变异系数，从零规划时这些**不存在**，存量纠偏时这些**躺在日志里**。


|  | 从零规划（还没有流量） | 存量纠偏（有流量，但旧规划/压测不靠谱） |
|---|---|---|
| 需求侧常数来源 | 业务算术：日活 × 人均请求 × 每次 token 数；长度分布套 3.5 节负载画像原型 | 挖历史日志：实测流量曲线、峰值系数、长度分布、变异系数 |
| 误差大头 | 需求侧（猜的），远大于供给侧 | 旧误差常在压测方法本身（用第 6 章十秒判定旧报告） |
| 常数表达 | 给区间不给点值，附 ρ 四档敏感性表 | 给实测值，附与旧假设的差异 |
| 资金原则 | 可逆性优先：云 > 租赁 > 自购（见 7.3 回本点），起步最小化，大额不可逆采购推迟到有真实流量之后 | 纠偏先花小钱：先流量治理（限流/分级额度/前缀缓存/错峰），再谈买卡 |
| 压测的角色 | 验证"假设成立时系统扛得住"，不是验证假设本身 | 先诊断旧压测错在哪（闭环当容量？定长自欺？没算峰值系数？），再用开环压测重新锚定 |
| 上线/落地后 | 第一天就设计好日志字段（请求时间戳、输入/输出 token 数、会话 ID），首批真实流量积累后尽快再校准——规划是等待被数据推翻的草稿 | 验收三件套：实测 ρ 回落到目标档、P95 达标、单 token 成本下降 |
| 特有陷阱 | 把猜的数字写成精确值，误导采购决策 | ① 历史≠未来：增长趋势单独建模，峰值系数里不含增长；② 存量系统有惯性：模型、额度体系、用户习惯已定型，纠偏分阶段，别指望一次到位 |

一句话：**从零规划买的是可逆性，存量纠偏挖的是日志；前者怕买错，后者怕看错。**


### 7.1 算例：500 万 DAU 智能客服

需求：500 万 DAU（日活跃用户数）× 8 轮/日；PAR=3；输入 2048 / 输出 512；SLA：TTFT P95≤2s，TPOT≤50ms，E2E P95≤30s。方案：Qwen2.5-72B FP8，vLLM，8×H100。

**负载**（HTTP 请求级口径，见第 0 章）：λ_avg = 500万×8/86400 ≈ 463 QPS → λ_peak ≈ 1389 QPS；若按会话级对外汇报：500 万会话/日，单会话成本 = 8 × 单请求成本

**SLA**：如上

**单机**：λ_sat ≈ 8.6 QPS（算例 A），锚定后取 8.0；S≈3.0s，c≈26

**ρ_target**：在线取 0.70

**排队核算**：n=249，a=18.2，C≈0.06~0.12，t95_q≈0.3~0.6s → E2E P95 ≈ 10~13s，TTFT P95 ≈ 0.3~0.7s，全部满足

**节点规划**：249 + 2% 冗余 ≈ **254 台（2032 卡）**；档位对比见下

**压测验证**：open-loop 扫 2/4/6/8/10 QPS，验证拐点；上线后滚动校准


| 方案 | ρ | 节点数 | P95 排队 | 结论 |
|---|---|---|---|---|
| 保守 | 0.50 | 348+7 | ≈0s | 体验极致，卡多 40% |
| 推荐 | 0.70 | 249+5 | ≈0.5s | 性价比拐点 |
| 激进 | 0.85 | 205+4 | ≈3s | 省 17% 卡，高峰抖动 |
| 玩火 | 0.95 | 183+4 | ≈11s | 突发即雪崩 |

模型选型是最大杠杆：同样的量换 7B（单卡 H100，λ_sat 25+ QPS/卡），节点数降一个数量级。规划报告应永远附”大模型 vs 小模型+路由”对比。


#### 7.1.1 逐行推演：249 台是怎么算出来的（第一次看先读这里）

上面七行是结论速写，这里把每一步的“为什么”拆开。核心公式只有一个：n = ceil(λ_peak ÷ (λ_sat × ρ_target))，难点在于每个输入从哪来、为什么不能换。

【第 0 步｜把业务语言翻译成流量】500 万 DAU × 每人 8 轮 = 4000 万次调用/日。÷86400 是把“一天的总量”摊成“每秒平均多少请求”：4000万 ÷ 86400 ≈ 463 QPS，这叫 λ_avg。但流量不是均匀的——晚高峰通常是日均的 2~5 倍（这就是峰值系数 PAR，取 3），所以 λ_peak = 463 × 3 ≈ 1389 QPS。容量必须按 λ_peak 配：按均值配 = 每天高峰准时宕机。

【第 1 步｜单机到底能扛多少】λ_sat ≈ 8.6 QPS 不是自己算的，是第 3 章算例 A 的产物：Qwen2.5-72B FP8 × 8×H100，用 roofline 算出理论上限、再用 MFU 实测常数锚定。这里再打个折取 8.0——理论值锚定后仍偏乐观，留 7% 余量是给“常数会漂移”交的保险费，这是全书的纪律：裸用不锚定的常数，误差 30% 起步。

【第 1.5 步｜另外两个单机参数】S ≈ 3.0s 是服务一个请求的平均耗时（输入 2048 + 输出 512 的混合口径，含 prefill 与逐 token 生成）；c ≈ 26 是单节点能同时装下的请求数，即 KV Cache 槽位（2.3 节那个“隐形天花板”——显存装不下的并发，算力再强也用不上）。

【第 2 步｜给自己划利用率红线】ρ_target 取 0.70。为什么不能拉满到 1.0？回到第 1 章饭店模型：利用率越接近 100%，排队时间越爆炸（ρ=0.95 时平均等待是服务时间的 19 倍）。0.70 的意思是每个节点只敢用到七成，剩下三成是给流量波动和排队留的活命空间。在线服务经验区间 0.5~0.75（见 4.3 对照表）。

【第 3 步｜核心算术：节点数 n】每个节点计划承担 λ_sat × ρ_target = 8.0 × 0.70 = 5.6 QPS。于是 n = ceil(1389 ÷ 5.6) = ceil(248.04) = 249 台。注意向上取整不能省：248 台意味着全集群按 100.02% 红线运行，没有任何余量。

【第 4 步｜排队核算：验证 SLA 而不是假设 SLA】单节点到达率 λ_node = 1389 ÷ 249 = 5.58 QPS；流量强度 a = λ_node × S ≈ 5.58 × 3.2 ≈ 18 Erlangs。拿 a 和 c=26 去查第 4 章排队模型（4.3 对照表附近）：等待概率 C≈0.06~0.12，排队 P95 约 0.3~0.6s。于是 TTFT P95 ≈ 排队 + prefill ≈ 0.3~0.7s（SLA 2s ✓）；E2E P95 ≈ 服务时间 P95（约 10~12s）+ 排队 ≈ 10~13s（SLA 30s ✓）。这一步的本质：n 是按“平均账”算的，SLA 是“尾部账”——尾部账必须用排队模型单独核，不能默认平均达标尾部就达标。

【第 5 步｜冗余与卡数】249 × 1.02 ≈ 254 台，每台 8 卡 = 2032 卡。2% 冗余干什么用：故障机替换、滚动升级、冷启动预热（8.4 节）——没有冗余池，每次发版都在赌运气。

【第 6 步｜算完不算完，必须压测验证】用开环压测扫 2/4/6/8/10 QPS（6.5 节 SOP），看实测拐点是否落在 8 QPS 附近；上线后用真实流量滚动校准 λ_sat。规划值和实测值的差，就是你下一次规划的常数修正量。

【第 7 步｜别忘了最大的杠杆不在算术里】换 7B + 路由，单机 λ_sat 从 8 涨到 25+ QPS，节点数降一个数量级——同样 2032 卡的预算，纠结 249 还是 254 是省 2%，换模型是省 90%。所以规划报告永远附“大模型 vs 小模型+路由”对比：算术决定你要买多少，选型决定你要不要买。

【常见疑问】Q：为什么 λ_sat 要乘 ρ_target 才去除？A：λ_sat 是“不排队时物理上能跑多少”，乘 ρ_target 才是“答应客户 P95 前提下敢用多少”——前者是物理，后者是承诺。Q：a=18.2 和我算的不一样？A：取决于 S 取 3.0 还是 3.26 的口径，差 8% 以内不影响结论——常数误差管理的实战一例。


#### 7.1.2 对照算例：同一业务改用 P/D 分离怎么配（含「为什么不省卡」的反转）

同一需求（λ_peak=1389 QPS，输入 2048 / 输出 512，72B FP8 × 8×H100），把 7.1 的一体化部署换成 P/D 分离。方法见 3.6，这里走一遍完整数字。结论先行：这个负载下分离总卡数反而上升 55%~80%——P/D 分离买的不是卡，是 SLA 稳定性与独立扩缩。

【P 池：按算力配】λ_P = n×F×MFU ÷ (2×N_active×L_in)。代入：8×989 TFLOPS × MFU ÷ 3.6×10^14 FLOP/请求（含注意力项，同算例 A 口径）。关键假设：纯 prefill 批没有 decode 穿插干扰，MFU 可从 0.40 提到 0.55（待锚定，这是本算例唯一的自由参数）。λ_P = 8×989×0.55 ÷ 360 TFLOPS/请求（即 3.6×10¹⁴ FLOP 的同口径换算）≈ 12.1 QPS → n_P = ceil(1389 ÷ (12.1×0.70)) = ceil(163.9) = 164 台。敏感性：若 MFU 只有 0.40，λ_P=8.8，n_P=226——又一处「常数不锚定，预算差 38%」。

【D 池：按驻留时间配】每请求在 D 节点驻留 L_out × TPOT_D = 512 × 5.7ms ≈ 2.9s（TPOT_D 用算例 A 闭式解，分离后无 prefill 抖动，该值更稳）。单槽位吞吐 1/2.9 ≈ 0.34 req/s，节点 26 槽 → λ_D ≈ 8.9 QPS → n_D = ceil(1389 ÷ (8.9×0.70)) = ceil(223) = 223 台。

【KV 传输核算：分离的入场券】每请求 P→D 搬运 L_in × kv_per_token = 2048 × 320KB ≈ 640MB。25GbE（约 3GB/s）需 0.21s——TTFT 直接破 SLA；400G IB（约 50GB/s）需 13ms，可被流水线重叠（判据见 3.6：传输时间 < D 节点单步 decode 时间则 TTFT 增量≈0）。结论：没有 IB 级网络，P/D 分离免谈。

【总账对比】分离：n_P+n_D = 164+223 = 387 台（MFU 乐观）~ 449 台（MFU 保守），加冗余约 395~458 台；一体：249+冗余 = 254 台。为什么分离反而费卡：一体机的 chunked prefill 让 prefill 和 decode 共享同一批 SM 的空隙，总算力被池化利用；分离后两个池各自留 ρ_target 余量，余量不能共享。这是「资源交换」的又一次现身：你用更多节点，换 SLA 稳定性和扩缩独立性。

【那什么时候反转？】按 3.6 判据逐条对：① L_in/L_out 越大越划算——本例 4:1 刚及格；若输入涨到 16K（RAG/文档场景），一体机里每次 prefill 抢 16K token 的算力，TPOT 抖动拖垮 D 侧 SLA，分离立即占优；② 前缀复用率——本例多轮对话 h 可达 0.5~0.9，P 池前缀缓存命中后 λ_P 放大 1/(1−h)，n_P 直接砍半，反转开始；③ TPOT SLA 越严越要分——本例 50ms 很宽松，若收紧到 20ms，一体机 prefill 插入抖动（4.5 节队头阻塞）很难过线。三条占两条，就上分离。

【决策一句话】先算总卡数对比（分离通常不省卡），再按「输入长度 / 前缀复用 / TPOT SLA 严格度」三条判据定性；规划报告里 P/D 分离方案和一体化方案必须同表对比——只报分离方案的节点数，等于隐瞒了它多花的卡。

**【补记：P/D 分离还可以“异构分派”】**上例两个池用的是同一种卡，前沿实践（LMSYS V4-Pro × H20，L3）已按角色分派不同档位：P 节点不留长期状态，配显存较小的 H20-96GB；D 节点要长期驻留每个请求的 KV，配 H20-141GB（带宽还从 4.0 提到 ~4.8 TB/s）。规划含义：P/D 分离的成本账（7.2/7.3）里两个池的**卡型可以不同价**——P 池买算力、D 池买显存带宽，各买各的甜区，比统一采购再省一笔；异构分派也让“分离费卡”的结论多一个变量：费的可能是台数，省的可能是总价。

【反转后的账：输入换成 16K 重算一遍】同一业务（λ_peak=1389，输出 512），输入 2048 → 16384（RAG 长文档），常数同算例 A（L2 级估算，MFU 增益待锚定）。一体机：每请求算力 = prefill 2.77×10^15 FLOP（含注意力项）+ decode 0.74×10^14，λ_compute ≈ 3165e12 ÷ 2.77e15 ≈ 1.141 QPS → n = ceil(1389 ÷ (1.141×0.70)) = 1740 台。分离：P 池 λ_P = 8×989×0.55 ÷ 2.7e15 ≈ 1.612 QPS → n_P = ceil(1389 ÷ (1.612×0.70)) = 1231 台；D 池不受输入变长影响 → n_D = 223 台不变；合计 1454 台。省 286 台 ≈ 2288 张 H100 ≈ 16%。

【反转后的三重收益】① 卡数：省 16%（上面已算）；② SLA（通常比卡值钱）：一体机单次 16K prefill 吃 0.85s 算力，chunked 摊开后 TPOT 周期性飙升，20ms 的 TPOT SLA 基本守不住；分离后 D 池 TPOT 稳定在 ~5.7ms，P95 敢写进合同；③ 扩缩独立性：输入变长只扩 P 池、输出变长只扩 D 池，多轮对话前缀命中 h=0.8 时 P 池 λ_P ×5，n_P 从 1231 砍到约 250 台——这个杠杆一体机用不了。

【最终判据一句话】4:1 时分离是「消费」（多约 55% 的卡买稳定），32:1 时是「投资」（省 16% 的卡还送 SLA）——是消费还是投资，判据就藏在 L_in/L_out、前缀复用率、TPOT SLA 严格度三个数里，算完再表态。


### 7.2 成本换算：从技术容量到钱（CTO 视角）

单 token 成本 = (n_节点 × 单节点每小时成本) / (λ_peak × 3600 × 每请求总token)

**关键修正：吞吐必须按 λ_sat × ρ_target 计（含体验溢价），不是按 λ_sat 计**。

ρ_target 从 0.7 提到 0.95：单 token 成本降 ~26%，代价是 P95 恶化 10 倍——**成本-体验权衡就是 ρ 的选择**，这是给管理层讲的核心交易。

小模型+路由：若 70% 请求可路由到 7B，综合单 token 成本可降 5~10 倍。

离线批处理（评测/数据合成）可安排在低谷时段共用在线集群：ρ 拉到 0.9+，边际成本近零（见 8.1）。

**三种成本口径**（按需取用）：


| 口径 | 公式 | 用途 |
|---|---|---|
| 每百万 token | 时租 / (吞吐 × 3.6) | 与 API 定价对标 |
| 每请求 | 时租 / 3600 × E2E秒数，E2E =(TTFT + L_out×TPOT)/1000 | 单次调用成本 |
| 每用户每月 | 时租 / (并发用户× 8 ×22) | 按工作日 8 小时 × 22 天 |


### 7.3 自建 vs 云：算清回本点

自建集群的真实小时成本远不止买卡的钱，拆成五块（含义｜怎么算｜典型取值）：

- **折旧**：一次性购置款（CAPEX）摊到使用年限 = CAPEX / 折旧年限。典型：一台 8 卡整机按 3~5 年（常取 4 年）折旧。
- **电费** = GPU数 × TDP × 占空比 × PUE × 8760 / 1000 × 电价。TDP = GPU 额定满载功率；占空比 0.3~1.0；PUE 见下表；8760 = 一年小时数。
- **托管（colo）** = 每机柜月租 × 12（机位、网络、基础制冷）。
- **维护** = CAPEX × 维护率，典型 5~10%/年（保修、备件、坏卡更换）。
- **人力**：运维工程师摊销，小团队也是一笔固定年起数。
**年成本 = 折旧 + 电费 + 托管 + 维护 + 人力**；换算成"每 GPU/小时"时，分母里的**利用率至关重要**——一台只用 60% 的卡，每有效小时的摊销成本要除以 0.6（凭空贵 67%）。

**回本点**：逐月累计，云累计成本首次超过自建累计成本的那个月。月运营 = 年成本里除折旧外的部分 ÷ 12（折旧已在自建累计里一次性计入）；云累计 = 每小时云价 × 730 × 利用率 × 月数（730 = 8760÷12）。直觉：**自建是"一次性大投入 + 低边际"，云是"零首付 + 高边际"**——利用率越高、用得越久，自建越划算；短期或波动负载，云更灵活。

**PUE（Power Usage Effectiveness，电源使用效率）** = 数据中心总能耗 ÷ IT 设备能耗，常被低估：


| 环境 | PUE |
|---|---|
| 超大规模数据中心 | 1.1 |
| 专业托管（colo） | 1.4 |
| 企业机房 | 1.8 |
| 普通办公室 | 2.2 |

PUE 1.4 意味着每 1 度电用在 GPU 上，就要额外花 0.4 度在散热供电上。另外电源（PSU）选型还要在裸功耗上加 25% 余量。


### 7.4 混合负载的容量分配：白天营业厅，夜里搬金砖

真实业务几乎从不是纯交互或纯跑批，而是混合。关键认知：**交互和跑批抢的是同一个 decode 资源**（瓶颈侧），裸混的结果必然是跑批挤破交互的尾延迟——VIP 正在被服务，后门进来一卡车批货，柜台全去搬货了。

首选分时（90% 客户的真实形态）：白天按 λ* 保障交互，夜里机器闲着也是闲着，跑批是白捡的产出——**白天是营业厅，夜里是清点金库，同一套设备两份产出**。跑批不承诺容量，只利用闲时。

必须白天混跑时的铁律：交互流量按 λ* 封顶放入；跑批设低优先级 + 速率上限，只吃剩余余量（引擎优先级队列，或给跑批单开一个限速入口）。可给的跑批量 ≈（μ − 当前交互占用）× 0.7。

跑批溢出的三道保险（怕夜里跑不完、拖到早上撞交互）：①接单先算工时（6.7 的 ETA 公式），装不下的拆两晚；②早 8 点自动闸——跑批客户端到点降速或挂起；跑批天然断点续跑（每单独立、完成即落盘、没跑的明晚接着跑）；③优先级让路——白天真撞上，交互优先、跑批压到地板速率，交互客户无感。一句话：**押运车早上 8 点必须离场，没清点完的先封存，明晚再清。**
