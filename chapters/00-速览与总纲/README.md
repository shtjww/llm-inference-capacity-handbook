## 0. 一页纸速览

任何「给我 N 张卡，能扛多少 QPS？」的问题，答案由**三层**决定：


| 层 | 回答的问题 | 核心公式 | 大多数人漏了吗 |
|---|---|---|---|
| 物理层 | 理论上限多少？ | Roofline（屋顶线模型，见 2.2）：Prefill 看算力，Decode 看带宽，并发看显存（KV Cache） | 有人会算 |
| 系统层 | 单节点实际服务能力 μ？ | λ_sat = min（算力墙, TPOT-SLA 墙, KV 槽位墙） | 90% 漏掉 Prefill 抢 Decode 资源 |
| 排队层 | 真实流量下 P50/P90/P95？ | 排队论：E[W] ∝ ρ/(1−ρ)，P95 在 ρ→1 双曲线爆炸 | 几乎所有人都漏 |

**七句话结论：**

1. **闭环压测（并发打满）只能测出上限 λ_sat**，测不出用户体验——它隐含 ρ=100%，而 ρ=100% 时排队等待趋于无穷。

2. 真实容量 = λ_sat × ρ_target（目标利用率，在线业务 0.5~0.75），不是 λ_sat。留余量是数学决定的，不是工程能"优化"掉的。

3. **方差和均值一样重要**：排队时间乘以 (Ca²+Cs²)/2，长文本混部下该系数常达 3~6。

4. **每个常数都必须能回答三个问题：从哪来、误差多大、怎么测准**。MFU/MBU 等效率常数必须锚定：实测 > 仿真 > 公开基准 > 经验值；裸用经验值误差 30%+，671B 级外推（超出实测锚点范围的估算）可达数倍。

5. **公式给的是区间不是点**：常数不确定 → 结论必然是一个区间。诚实交付 = 给区间 + 标注误差预算，而不是给一个漂亮的确数。

6. **MoE（混合专家）模型两条腿分开算**：算力侧用激活参数（DeepSeek-R1/V3=37B），访存/显存侧用总参数（671B）。

7. **前缀缓存命中率是长输入业务的生死线**：h=0.9 时等效输入缩 10 倍、λ_compute 放大 ~10 倍——规划按业务实测命中率修正，压测必须带重复前缀（定长随机数据 h=0，自欺欺人）。

**七步 SOP**：定义负载 → 定义 SLA → 算单机 λ_sat（锚定常数）→ 定 ρ_target → 排队模型算 P95 → 节点规划（含成本）→ 开环压测校准。

**闭环总装**：上面七步只走到“上线前”——全链路是一个环，不是一条线：公式估算（给区间不给确数，第 4 章“三件套”）→ 仿真海选（校准需求侧常数 PAR / Ca² / Cs²，第 5 章两阶段工作流）→ 开环压测（锚定供给侧常数 MFU / MBU / λ_sat，第 6 章 SOP）→ 上线后日志回锚（重测 PAR 与 Ca²、滚动校准 λ_sat，第 6 章）→ 回算修正下一次规划。任何一环省掉，规划就退回拍脑袋；余量堵“机器会坏”，堵不住“常数错了”和“负载变了”。

**请求计数口径（先对齐再谈数字）**：本手册所有 λ、QPS、并发数，默认指 **HTTP 请求级**（一次 API 调用 = 1）；多轮对话里"一轮 = 一个请求"。


| 口径 | 一个"请求"指什么 | 谁在用 |
|---|---|---|
| HTTP 请求级（默认） | 一次 API 调用；多轮对话每一轮算一个 | 网关、压测、容量规划 |
| 业务会话级 | 用户完成一个完整意图（可能含多轮） | 产品、财务核算成本 |
| Token 级 | 每生成一个 token 算一次计算（TPS，tokens/秒） | GPU 算力评估、常数锚定 |

换算：业务会话 QPS = HTTP 请求 QPS ÷ 平均轮次；单会话成本 = 单请求成本 × 平均轮次。**口径不对齐，4000 万次调用会被听成 4000 万用户。**


## 0.5 总纲：三条纪律（全手册的脊柱）

本手册所有章节，是同一条优化纪律在不同层的实例。记住三句话，全书公式都能自己长出来：

① 测出瓶颈在哪一层，不猜。物理层问“算力、带宽、显存哪个先到顶”；系统层问“三面墙哪面最矮”；排队层问“等待从哪冒出来”。任何一个环节，同一时刻只有一个瓶颈资源。

② 用富余资源换瓶颈资源，方向反了就是负优化。例：H20 带宽 4TB/s 虚胖、CUDA core 算力孱弱（~44 TFLOPS，万亿次浮点运算/秒），INT4-marlin（4 位整数量化方案），花稀缺算力省富余带宽，高并发实测比 BF16（16 位浮点精度）还慢 16%——量化不是越狠越好，交换前先确认哪种资源稀缺。

③ 动手前算阿姆达尔账（阿姆达尔定律：优化单个环节后，整机提速上限 = 1÷(1−p)，p = 该环节占总时间的比例）：收益 = 幅度 × 占比，天花板 = 1÷(1−p)。实测例：RMSNorm（归一化）kernel 比 vLLM 生产实现快 35%，但它在 decode 一步中占比约 1%，整机吞吐只 +0.14%；FP8（8 位浮点精度）动的是占比约 60% 的 GEMM（矩阵乘运算），整机 +25%（64 并发）~ +44%（单并发）。占比决定上限，技术只决定离上限多近。

章节映射：物理层 = 瓶颈识别；系统层“三面墙取最小” = 瓶颈的代数化（就是算账）；排队层 = 占比随负载漂移——阿姆达尔的服务级推广：p 不只随业务画像变（见 3.5），还随 λ 变——接近饱和时排队主导 E2E（端到端时延），会吞掉一切微观优化的收益。

两个视角在此汇合：容量规划从上往下（给定算力能扛多少 QPS，第 7 章七步流程）；优化决策从下往上（改了这个零件值多少钱，先问三句话——瓶颈在哪、拿什么换、幅度×占比够不够回本）。
