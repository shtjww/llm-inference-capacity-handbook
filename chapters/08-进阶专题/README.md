## 8. 进阶专题：投机解码、多模型路由与冷启动

本章回答：两个最常用的"省卡大招"到底能省多少、什么时候失效；以及扩缩容场景常被忽略的冷启动账。原则与全书一致——**公式给形状，常数靠锚定，收益不计入基线**。


### 8.1 投机解码：用算力换带宽，所以大 batch 失效

**机理**：草稿模型每轮猜 γ 个 token（便宜），目标模型一次前向并行验证 γ+1 个（权重只读一次）。单 token 接受率 α 时，每轮期望接受长度：

E[a] = (1 − α^(γ+1)) / (1 − α)      （α=0.8、γ=4 → E[a] ≈ 3.1）

**关键洞察：验证步骤是 Prefill 性质（γ+1 个 token 并行计算），不是 Decode 性质**。由此得两区制：


| 区间 | 验证步骤瓶颈 | 有效 TPOT 修正 | 结论 |
|---|---|---|---|
| 小 batch（带宽受限） | 权重读一次摊给 E[a] 个 token | TPOT × (1+γ·c_d)/E[a]，c_d = 草稿相对成本（0.05~0.3） | 加速 1.5~2.5 倍，λ_tpot 墙上移 |
| 大 batch（算力受限） | γ+1 个并行 token 吃 Prefill 算力 | 修正系数 →1 | 零收益甚至负收益 |

**实证佐证**：R1 × 8×H20 实测开/关投机解码吞吐 138.09 vs 138.11 tok/s——batch 已摊薄带宽、负载 prefill 主导，投机解码无可奉献。

**低 batch 端的最新佐证（L3）**：LMSYS 的 DSpark 在 V4-Pro × H20 上把单用户（batch=1）从 38 提到 172 tok/s（4 倍以上）——小 batch 端的收益上限比 1.5~2.5 倍的历史区间更高（1.6T MoE 的 decode 访存极重，投机摊薄效应更强）。另有两个新的工程要点：① 高并发下投机会引入**新长尾**——候选重打分（refinement）要做全词表投影，逐行点积让每个活跃请求反复读整套词表权重，合并成单个转置 GEMM 后单卡吞吐 +22.8%——大 batch 端不是“零收益”，而是“收益被新瓶颈吃掉”，拔掉钉子仍有得拿；② 跨 PP 部署时草稿器只在最后一个流水段，每轮投机都要跨段协调，需要引擎级协议支持（DSpark 的统一执行协议）——PP 部署评估 SD 收益前，先确认引擎支持。

**容量模型用法**：λ_sat 三面墙公式不变，TPOT 乘以修正系数 f(α,γ,B)，两区制插值：B→1 取 (1+γ·c_d)/E[a]，B>32 取 1。

**锚定方法**：α 不可理论预测（依赖业务分布、温度、草稿模型质量）——vLLM / SGLang 均暴露 acceptance rate 指标（SGLang 为 avg_spec_accept_length），开投机解码（SD）跑一次真实流量即得；γ 通常 3~5，EAGLE 类草稿 α 常见 0.6~0.85。

**三条纪律**：

1. **SD 收益不计入基线容量**——α 随业务漂移，只当冗余 bonus；

2. **失效判据**：batch > 32 或实测 α < 0.5，直接关掉（省草稿显存和调度开销）；

3. 草稿模型本身占显存，c_kv 墙要重算。

**草稿路线谱系（原理｜是否需训练｜开销｜加速比）**：


| 路线 | 原理 | 需训练 | 显存开销 | 加速比 |
|---|---|---|---|---|
| draft_model（草稿模型） | 小模型（大模型的 1/10）自回归猜 γ 个，大模型一次验证 | 无需：同系列同词表现成小模型（如 70B 配 8B） | 额外小模型权重 + KV | 1.5~3× |
| Medusa（美杜莎头） | 最后一层接多个并行预测头，一次前向预测多个位置 | 需要：基座冻结，单训预测头 | 仅多几个轻量头，增量很小 | 1.5~2.5× |
| EAGLE v2/v3 | 轻量自回归头在特征层面外推，复用大模型中间特征 | 需要：训练轻量自回归头 | 小 | 3~6.5×（目前最强） |
| Lookahead（前瞻解码） | Jacobi 迭代 / n-gram 并行猜测 | 完全无需（即插即用） | 近 0 | 1.2~2× |
| prompt_lookup（提示查找） | 从 prompt 检索重复片段当猜测（改写/摘要/RAG 复述场景） | 完全无需（纯检索） | 近 0 | 1.5~3× |

一句话权衡：**免训练的**（draft_model 借现成小模型、Lookahead/prompt_lookup 纯算法）即插即用但加速有限或依赖场景；**需训练的**（Medusa/EAGLE）先付训练成本，EAGLE 换最高加速，常驻高负载服务最值得。DeepSeek 系的 MTP（多 token 预测）同属此列——注意**量化版本是否保留 MTP 头**是不同部署批次的关键差异（直接影响 accept length 与 decode 速度）。

**离线批处理（batch mode）**：任务没有实时延迟要求时（批量文档处理、数据标注、评测），就该把吞吐榨干——最大 batch = ⌊空闲 KV 显存 / 每序列 KV⌋，聚合吞吐 = 最大 batch × 单序列 decode 吞吐 × 0.90（批处理利用率系数，高于实时的 0.85）。**聚合吞吐通常是实时服务的 2~3 倍，单位 token 成本显著更低**——代价是单条请求延迟完全不可控。这就是公有云 Batch API 能打五折的原因，也是"夜间批处理填谷"的理论依据。


### 8.2 多模型路由：多个独立 M/M/c 池 + 一道分流优化题

**模式一：静态分流（网关按意图/长度/用户等级分流）**

- 流量按分流比例 p_i 切到各模型池，每池独立排队（各自 M/M/c、各自 ρ_i、各自 SLA 校核）；
- 总成本 = Σ n_i × 单节点成本_i；优化：给定 λ_peak 与分流比例，网格搜索各池节点数使总成本最小——2~3 个模型就是一道小题；
- **隐性成本：路由错误率 = 质量 SLA**。"该去大模型的去了小模型"不体现在时延里，体现在准确率里——报告中必须单独标注。
**模式二：级联（cascade）（小模型先答，置信度不足升级大模型）**

- 小模型池看到**全量** λ（不是它最终回答的部分！），大模型池看到 e×λ（升级率 e 实测常见 0.1~0.3）；
- 升级请求时延串联：P95_total ≈ P95_small + P95_large，SLA 按和校核；
- **最常算错：按"小模型最终回答量"给小池配容量——应按全量**。
**算例**（承接 8.1，λ_peak = 1389 QPS，2048 进/512 出）：


| 方案 | 配置 | 总卡数 | 相对成本 | P95 与风险 |
|---|---|---|---|---|
| A 单模型（基准） | 72B × 8×H100，254 台 | 2032 | 100% | E2E P95 ≈ 10~13s |
| B 静态分流 70/30 | 7B 池 972 QPS：单卡 H100 λ_sat≈25、ρ=0.7 → ~56 卡；72B 池 417 QPS → ~75 台（417÷(8.0×0.7)=74.5，对齐 8.1 锚定口径） | ~656 | ~32% | 两池各自过 SLA；路由错误率须监控 |
| C 级联 e=0.3 | 7B 池按全量 1389 配（~80 卡），72B 池按 417 配（~75 台） | ~680 | ~33% | 升级请求 P95 串联 +1~2s |

结论：70/30 分流把总卡数从 2032 压到 ~656（约 1/3）——**模型选型与路由是整个容量规划里最大的杠杆，超过一切内核优化**。代价写在风险列里：路由错误率、串联时延、两个池的运维复杂度。


### 8.3 失效边界：什么时候这两招是负优化

- **投机解码**：大 batch 在线服务（验证抢 Prefill 算力）、低 α 业务（开放域创作）、Prefill 主导负载（长文档摘要——即 R1 场景）；
- **路由**：业务难度方差小（没有可分的"简单多数"）、路由错误代价高（医疗/金融）、流量太小——两个池的小 c 排队惩罚 > 分流收益；
- **通用判据**：分流后任一池的 c < 10，把该池 ρ_target 降一档（见 4.3：c 越小曲线翘得越早），再谈收益。

### 8.4 冷启动：一个副本多久能就绪

自动扩缩容和 Serverless（无服务器，按需弹性拉起副本）场景下常被忽略的一笔账：**从拉起一个副本到它能接第一个请求，要多久？** 冷启动时间 = 加载 + 编译 + 预热三段相加：

**加载** = 模型字节 ÷ 存储带宽。存储介质读盘带宽差异巨大：HDD 约 200 MB/s；SATA SSD 约 550 MB/s；NVMe Gen4 约 7 GB/s、Gen5 约 14 GB/s（模型盘主力）；并行文件系统（如 Lustre）可达 100+ GB/s。同一个 40GB 模型，HDD 上加载约 200 秒，NVMe Gen4 只要 5.7 秒——差 35 倍。

**编译**：框架把模型图编译/优化成可执行 kernel，= 基础时间 + 每十亿参数增量。vLLM/SGLang 约 30s + 1.5s/B；**TRT-LLM 约 300s + 10s/B**（70B 要约 1000s，但一次性，编好可缓存复用）；llama.cpp/Ollama 几乎免编译。

**编译制品的缓存纪律（TRT-LLM 部署必看）**：engine 是**不可变制品**，缓存键 = 模型版本 × 卡型号 × TRT 版本，三者任一变化都必须重建——**换卡型号不换 engine 是常见的发布事故源**（症状：性能莫名劣化或直接起不来）。工程做法：engine 纳管进制件库，CI 离线预 build，发布即取缓存（从几十分钟降到秒级），回滚 = 换回旧制品文件。

**预热**：CUDA Graph 捕获、显存分配器预热等，同样是基础时间 + 每十亿参数增量：vLLM ≈ 10 + 0.1×B（70B → 17s）、TRT-LLM ≈ 5 + 0.05×B、llama.cpp ≈ 2 + 0.05×B。

**运营含义**：① 冷启动时间必须算进自动扩缩容的 SLA——突发流量来了要等 158s 才有新副本，期间的请求可能全部超时；② **TRT-LLM 首启最慢但运行最快**，适合常驻高负载服务；**llama.cpp/Ollama 冷启动约 20s**，适合频繁起停的弹性场景。


### 8.5 多模态与视觉输入：一张图 = 一次 Prefill 突发

视觉/多模态模型（Qwen-VL、LLaVA 系）不改变前三章的任何公式——变的是 **L_in 的构成**：图像先被切成 patch，每个 patch 折算成一个视觉 token，拼在文本 token 前面，然后走同一条 prefill/decode 流水线。

**视觉 token 账**：token 数 = (H ÷ patch_size) × (W ÷ patch_size)。以 patch_size=14 为例，1024×1024 的图 ≈ 73×73 ≈ 5300 个视觉 token（早期实现按 64×64=4096 计）；KV 占用与文本 token 完全同价（70B FP16 约 320KB/token → 一张大图 ≈ 1.3GB KV）。**一张图 ≈ 一个数千 token 的 prefill 突发**；视频更狠：token 数 ≈ 抽帧数 × 单帧 token，一条视频轻松破万。

与纯文本推理的三个关键差异：

1. **一次性全量到达**：文本 prompt 可以 chunked prefill 切块慢慢算；视觉 token 之间有空间关系、通常整图一起算，瞬间挤占整个 token 预算——第 4.6 节的预算闸门对图像流量更敏感。（工程上，vLLM 等主流实现长期对多模态输入默认关闭 chunked prefill、整图按一个调度单元处理；新版引擎在逐步放开，以所用版本实测为准。）

2. **输入长度方差暴增**：分辨率、张数、帧数都是业务变量，同一接口的 L_in 可以从几百到几万——Cs² 被显著拉大，4.2 排队公式里 (Ca²+Cs²)/2 的惩罚比文本场景重得多。

3. **Prefill 显存峰值更高**：所有视觉 token 的激活同时驻留，prefill 阶段峰值明显高于 decode。

**容量规划做法不变，改的是输入口径**：把“平均视觉 token 数”并入 L_in（按业务画像折算：平均每请求图数 × 单图 token 数），算力墙公式照用、λ_sat 照压——只是别再拿纯文本 prompt 去压多模态服务，那是自欺欺人。缓解手段按性价比排序：限制最大分辨率/张数（最直接）、视觉 token 压缩/合并、大图切 tile 分批、先文后图延迟加载。


### 8.6 适用边界：非 Transformer 架构（Mamba/SSM 类）

本手册的三层模型为 Transformer 量身打造，遇到 Mamba 这类状态空间模型（SSM）要重新清点家当：SSM 没有 KV Cache——状态是定长矩阵，与序列长度无关——**KV 槽位墙直接消失**，显存压力只剩权重与激活，并发上限不再随上下文长度线性腰斩，系统层退化为纯 Roofline（算力墙 + 带宽墙两面墙）；decode 每步从“读 KV”变成“更新定长状态”，带宽墙的判断逻辑不变但量级大减。**排队层结论全部保留**——ρ、P95 爆炸、瞬态修正与架构无关。混合架构（Jamba 类，Transformer 层与 SSM 层混排）按 Transformer 层的比例折算 KV。一句话：**SSM 时代本手册的第 2、4 章继续管用，第 3 章的三面墙变两面墙**。
