## 9. 集群与基础设施

当单卡放不下、单机扛不住，就要进入分布式。本章回答：怎么切分模型、要多大网络带宽、多少存储和内存。（部分内容源自训练场景，推理只取所需——推理不做反向、没有梯度同步，**只需要 TP 和 PP，不需要 DP**，要扩吞吐直接加副本。）


### 9.1 并行策略：TP / PP / DP 的分工

**TP（张量并行，Tensor Parallelism）**：把每一层的矩阵切开放到多卡，卡间需要高频通信，**只在节点内（NVLink）用**。TP 上限取 min(8, 每节点GPU数)，且受 GQA 约束——**TP 必须整除 KV 头数**（否则 KV 头没法均分）。

**PP（流水线并行，Pipeline Parallelism）**：把不同层放到不同卡，像流水线一样传递。容量按每卡 60% 估（留 40% 给 KV 和激活）。

**DP（数据并行，Data Parallelism）**：整模型多副本，各跑各的数据——推理扩吞吐的标准方式。

求解顺序：先用 TP 把单层塞进节点内、再用 PP 把层数摊开到够放下模型、最后用剩余的卡做 DP 扩吞吐。

> 训练侧捎带（推理部署用不上，自己微调时会踩）：容器里跑 PyTorch DataLoader 多 worker 时，默认 /dev/shm 仅 64MB 会直接崩，需 --shm-size 调大或改 num_workers。

10.1+ 显存账：TP / DP / EP 在每张卡上各放什么（初学者三迷，配实战案例）

**并行策略的通信分工上文已讲，这里补另一半账——显存。三种并行对显存的作用完全不同，混用是容量估算的第一大坑：**

【名词先钉死：rank 是什么】rank = 并行组里一个成员的"工号"，一个 rank 对应一个工作进程（推理时基本=一张卡一个 worker 进程）。编号分两档：全局大排行 global rank（0 到 总卡数−1）、小组内排行 local rank（如节点内 0~7）。三种并行各拉各的组：TP 组 = 同一引擎内合切矩阵的几张卡；DP 组 = 各引擎副本之间对表；EP 组 = MoE 专家发牌的全员大群（开 EP 时包含全部 DP×TP 个 rank）。所以推理语境里"一个 DP rank"≈ 一个独立引擎实例（vLLM 里一个 EngineCore：自己的调度器、自己的 KV 池、自己的服务端口）。本节说"稠密按 rank 复制"，意思是每个引擎副本各装一份——不是每张卡各装一份。

① TP 是"切"：每卡权重 = 模型总量 ÷ TP。切的是每一层的矩阵，卡数越多每卡越轻。② DP 是"复制"：每个 DP rank 一套完整（已按 TP 切好的）权重 + 一份独立的 KV 池。DP=2 增加的是份数（集群总占用 ×2），每张卡的权重不变（仍是 总量÷TP）。③ EP 是"只切专家"（仅 MoE，需引擎显式开启，如 vLLM --enable-expert-parallel）：专家跨整个 DP×TP 组全局发牌均摊，EP 度 = DP×TP；稠密部分（attention、共享专家、embedding）仍按 TP 切、按 DP 复制。

每卡权重总账（MoE + 开 EP，生产标准姿势）：

每卡权重 = 稠密部分 ÷ TP ＋ 专家总量 ÷ (DP × TP)

未开 EP 时退化为：每卡权重 =（稠密＋全部专家）÷ TP，且专家随 DP 完整复制——"DP=2 复制 2 倍"只在这种情形下对专家成立。

【DP=2 开 EP 后，什么 ×2、什么 ×1】稠密层权重 ×2（每 rank 一份、份内 ÷TP）；专家权重 ×1（全局均摊不复制）；KV 池 ×2（每 DP rank 独立一份，互不共享）；请求流/吞吐 ×2（这才是 DP 的真正目的）。MoE 的精髓：显存买容量（专家只买一份）、算力按次付费（只算激活专家）——DP 复制的是接待能力，不是专家本体。

【一句话判定】Dense：DP=2 就是全部权重复制 2 份（每 rank 一份，rank 内 TP 再切），无条件成立。MoE：专家复不复制，开关在 EP 而不在 MoE——开 EP：只复制稠密部分，专家全集群一份；不开 EP：专家按 TP 切后随 DP 完整复制，此时与 Dense 无异。

【案例 A：稠密，同样 8 卡两种切法——顺带回答"DP=2 总显存到底增加吗"】72B FP8 ≈ 72GB。切法一 TP8：每卡 72÷8 = 9GB，一个引擎一份 KV 池，全集群权重总占用 72GB（一份）。切法二 DP2TP4：每卡 72÷4 = 18GB（每卡量只由 TP 决定，与 DP 无关），两个 rank 各扛一份 → 全集群权重总占用 144GB（两份），KV 池也是两份独立的。结论要记死：DP=2 时【每卡权重不变、全集群权重总显存 ×2】——多买的那一份不是浪费，换来的是两份独立 KV 池 + 两倍请求接待能力；但容量估算时若忘了这份×2，会把集群总显存需求少算一半。

【训练 DP 的直觉，搬到推理要修正】训练里 DP 的标准画面是"每卡一份完整模型 + 各自数据 + 每步梯度 all-reduce"，这个直觉搬到推理有一半对一半错。对的一半：推理 DP 也是复制——但没有梯度同步，且复制的单位是【rank（引擎副本）】不是卡：rank 内部若 TP>1，一份模型由多卡合扛（每卡 = 总量÷TP）。错的一半：MoE 开 EP 后，连"每个 rank 一份完整模型"都不成立——专家全集群只有一份，跨所有 DP×TP 个 rank 发牌均摊，rank 越多每卡专家越薄。一句话修正版：稠密部分按 rank 复制、专家全集群一份、KV 池按 rank 独立。

【案例 B：MoE 实战，GLM-5.2 昇腾实测】先交代 721 是什么：GLM-5.2 是约 720B 参数的 MoE，W8A8 量化（权重 int8 ≈ 1 字节/参数）的权重文件在磁盘上实测为 181 个分片 × 4GiB ≈ 721GiB——"721"就是要搬进显存的权重总量。2 节点 16 卡跑 DP2TP8 开 EP：EP 度 = DP×TP = 2×8 = 16，实测每卡权重 ≈44GiB ≈ 721÷16，公式与实测吻合——注意专家并没有因为 DP=2 而复制两份，是 16 张卡全局均摊一份。若错用训练式直觉"DP=2 每份完整复制"来估：721÷8（只除 TP）≈ 90GiB/卡 > 64GB HBM，会误判"装不下"；反过来做集群总预算时若忘了稠密部分和 KV 池要 ×2，又会误判"余量充足"——两个方向的错都出过事故。另一组：W4A8C8 权重 ~360GiB，8 机 PD 分离的 D 侧 DP8TP4 → EP 度 32 → 每卡 ≈11GiB，大 EP 度把每卡权重摊到极薄，腾出的显存全让给长上下文 KV 池——这就是 PD 分离 + 大 EP 的工程动机（超节点场景同理，见 10.6）。

【三迷排雷】① 把 DP=2 当 2 倍权重——MoE+EP 下专家不复制，错一倍；② 以为 KV 池跨 DP 共享——每个 DP rank 的 KV 池独立，c_kv 按单 rank 算、总并发 = c_kv × DP；③ 算 EP 度忘乘 DP——分母是 DP×TP 不是 TP，少乘一个 DP，每卡专家权重高估 DP 倍。


### 9.2 网络通信量：五种通信与互连决策

**一条统摄全章的纪律：让通信走近路。** 所有并行策略与拓扑选择的底层原理只有一句——*每层都同步的并行（TP、ZeRO-3）必须锁进节点内 NVLink 域；只在边界或每步末尾才同步的并行（PP、DP）才能跨机走 IB*。**同步频率决定互连路径**：同步越频繁，越要用近的、快的路。下面所有公式和决策规则都是这条纪律的注脚。

先认识主流互连及其带宽量级：

- **PCIe**：主板标准总线，Gen4 约 32 GB/s、Gen5 约 64 GB/s，最通用但最慢；
- **NVLink**：NVIDIA GPU 间专用高速直连，H100 约 900 GB/s，比 PCIe 快一个数量级，但只在节点内；
- **InfiniBand（IB）**：跨节点首选，HDR 200Gb/s ≈ 25 GB/s、NDR 400Gb/s ≈ 50 GB/s、XDR 800Gb/s ≈ 100 GB/s；
- **RoCE**：以太网上跑 RDMA，IB 的低成本替代。
五种并行通信各要搬多少数据：

**① Ring All-Reduce（DP 的梯度同步）**：每卡收发 ≈ 2×(n−1)/n × 模型字节，n 大时 ≈ 2×模型字节、**与卡数几乎无关**。朴素做法（参数服务器或全互发）中心节点流量随卡数线性暴涨；Ring 分两阶段（reduce-scatter + all-gather）把流量摊平到环上。量大但每步只一次，且能和反向计算重叠——这是 ring 成为大集群梯度同步标配的原因。

**② 张量并行 TP**：通信量 ≈ 4 × 层数 × 每步激活字节。系数 4 的来历：每个 transformer 层有两个被切分的并行块（注意力块和 MLP 块），每块前向需 1 次 all-reduce、反向又需 1 次——2 块 ×（前向 1 + 反向 1）= 每层 4 次，再乘层数，**是五种里最凶的**。

**③ 流水线并行 PP**：只在相邻 stage 边界传一份激活张量，量最小（没有层数因子）。

**④ ZeRO-3（全分片数据并行，训练向）**：参数、梯度、优化器状态全部切片分散到各卡，一步要前向 all-gather 参数 + 反向 all-gather 参数 + 梯度 reduce-scatter，共三轮全模型量级通信（≈3×模型字节）——省显存但费带宽。

**⑤ MoE all-to-all（专家并行的 token 路由）**：通信量 ≈ 2 × topK × MoE 层数 × token 激活字节。每个 MoE 层把 token 按门控分发到专家所在的卡、算完再收回（一发一收=系数 2），topK 越大、MoE 层越多，流量越大。

**把字节换成带宽需求**：所需带宽 = 每步通信字节 ÷ 步时（如 500ms）。

**互连决策规则**：

- **TP → 必须 NVLink**：通信量是 PP 的几十上百倍，且每生成一步都要做，只有 ~900 GB/s 扛得住——这是 TP 被锁死在节点内的根本原因；
- **PP → InfiniBand 即可**：每个 stage 边界只传一份激活，量最小；
- **DP / ZeRO-3 → InfiniBand**：每步一次（ZeRO-3 三次）全模型级通信，量大但可与计算重叠；ZeRO-3 建议 XDR。
一句话：**通信量从大到小是 TP ≫ ZeRO-3 > DP ≈ MoE > PP，互连也就从 NVLink 往 InfiniBand 递降**。

**【反例补丁：通信量小 ≠ 总耗时小——EP 与 TP 的取舍】**按上表 MoE all-to-all 通信量比 TP 小，直觉上 EP 该更快；但 LMSYS 在 V4-Pro 的 prefill 上反着选：弃 MoE-EP 改用通信量更大的 MoE-TP（L3）。原因是真实流量存在**专家倾斜（expert skew）**：少数热专家分到的 token 远多于平均，持有热专家的卡算得最久，所有卡都要在 combine（结果合并）一步等它——**通信总量虽小，等待时间却由长尾决定**。换 TP 后通信量更大，但全部跑在 900GB/s NVLink 上、耗时整齐可预测。一句话：**可预测的通信，比不可预测的不均衡便宜。** 规划含义：EP 仍是 MoE 显存切分的主力（10.6），但 prefill 重、负载画像偏斜明显的场景，要把“专家倾斜税”打进 EP 的收益预期——倾斜程度只有真实流量知道，又是“常数靠锚定”的一例。


### 9.3 网络拓扑、通信开销与扩展效率

**网络拓扑**随 GPU 规模升级：

- **≤8 卡（单节点）**：NVSwitch/NVLink 全互联，任意两卡 ~900 GB/s 直连，跑 TP=8 吃满带宽；
- **9–64 卡（单层胖树）**：节点经网卡接一层 leaf 交换机，节点内 NVLink、节点间 IB NDR。典型分工：节点内 TP/DP，节点间 PP；
- **65–512 卡（两层胖树 / 轨道优化 rail-optimized）**：leaf + spine 两层无阻塞。"轨道优化"让所有节点的同号 GPU 走同一条物理 rail，all-to-all 流量被分散到多条独立轨道，特别利好 MoE；
- **512+ 卡（三层 Spine-Leaf）**：按 pod 组织，1:1 收敛比，跨 pod 跑流水线并行。

> **轨道优化的运维前提（易踩的坑）**：rail-optimized 集群要求 **GPU 索引与物理 rail 严格对齐**。固件/驱动升级可能改变 PCIe 枚举顺序，同号 GPU 走错轨道，通信性能无声劣化——有团队报告 MFU 因此掉过十几个点（L4 轶事级，未经本手册实测，但机理成立）。**任何固件/驱动/网卡变更后，重跑 nccl-tests 并核对 NCCL_TOPO_DUMP_FILE 的拓扑标注**，再放量。
**各并行的"通信税"**（经验式，总开销为三者之和，上限 50%）：

- **TP 开销 ≈ 3.5% × log₂(TP)**：节点内每层多次 all-reduce，TP 每翻一倍多约 3.5%——8 卡 TP 约 10.5%，即 8 卡只能发挥出 ~7.2 张卡的性能（7.2 = 8÷(1+10.5%)，开销摊薄口径），所以 TP 不宜超过 8；
- **PP 气泡 ≈ (PP−1) / micro-batch 数**：流水线启动和排空阶段部分卡空转，micro-batch 太少时气泡很大；
- **DP 开销**：只在每步末尾一次梯度 all-reduce，扩展性最好、开销最低。
三种并行的通信税率差一个量级：DP 最便宜、PP 次之、TP 最贵——正印证 10.2 的互连决策。

**扩展效率随规模衰减**（加这么多卡，实际只发挥出其中 X% 的线性算力）：


| 总卡数 | 扩展效率 | 实际等效算力 |
|---|---|---|
| 8 卡 | 94.5% | ≈ 7.6 张卡在干活 |
| 64 卡 | 88.5% | ≈ 57 张卡在干活 |
| 512 卡 | 80% | ≈ 410 张卡在干活 |
| 1 万张卡 | 62.5% | ≈ 6250 张卡在干活，其余被通信/同步/气泡吃掉 |

这就是为什么超大规模训练昂贵得"不成比例"。**推理场景要简单得多**：不做反向、没有梯度同步，只需要 TP 和 PP——模型 ≤8 卡放得下就纯 TP（单节点 NVLink）；放不下就 TP + PP（节点内 TP、跨节点 PP，通信墙判据见 3.7）。


### 9.4 存储与冷启动介质选型

存储带宽阶梯（冷启动加载、检查点、模型盘共用这一张表）：HDD 约 200 MB/s；SATA SSD 约 550 MB/s；NVMe Gen4 约 7 GB/s、Gen5 约 14 GB/s；并行文件系统（Lustre）100+ GB/s。选型规则：≤200 MB/s 用 HDD，≤550 MB/s 用 SATA SSD，≤7 GB/s 用 NVMe Gen4，更高上并行文件系统。（推理场景的主消费是 9.4 的冷启动加载账；训练场景的主项是检查点 ≈ 16N 字节/个，且需校验"检查点写得过来吗"：所需写带宽 = 检查点大小 ÷ 时间预算。）


### 9.5 系统内存与 CPU

- **推理**：RAM ≈ 模型大小 × 1.5（mmap 内存映射加载 + 操作系统）；
- **训练**：RAM ≈ 聚合显存 × 2（梯度缓冲 + 数据加载；聚合显存 = 单节点所有 GPU 显存之和）；ZeRO-Infinity 把优化器状态卸载到 CPU，RAM 需求 ≈ 优化器状态字节，反而是内存大户；
- **CPU 核数**：经验式 核数 = 每节点GPU数 + 6（每卡 1 核数据加载 + 6 核 tokenization）。

### 9.6 国产卡部署 MoE：EP 通信与 MLA 优化

昇腾、寒武纪上跑 DeepSeek 这类 MoE，比跑稠密模型多两笔账。

**EP（专家并行）的通信账**：MoE 每层由路由器为每个 token 选出少数专家（DeepSeek-V3/R1 为 256 选 8）。专家并行（EP）把专家摊到多卡、每张卡只放一部分，于是 token 的隐状态向量必须跨卡搬运才能送到选中它的专家手里——每个 MoE 层两次 All-to-All 通信：先 **dispatch（分发）**，各卡把 token 的 hidden 向量按路由结果发给目标专家所在的卡；专家在本地算完 FFN；再 **combine（回收）**，把结果发回原卡、按路由权重加权求和，接续下一层。形象点说：包裹是 token 的 hidden 向量（hidden 维 × 精度字节），地址是路由结果，每张卡同时是寄件人和收件人。通信量（每卡、每个 decode 步、一个 MoE 层）≈ 2 × 本卡 token 数 × topK × hidden 维 × 精度字节 ×（1 − 1/EP 度）：系数 2 是 dispatch+combine 一发一收（与上文⑤同口径，⑤是“每 token、全模型”粒度，此处换成“每卡、每层”粒度）；topK = 激活专家数（R1 为 8）；（1 − 1/EP 度）是均匀路由下目标专家不在本卡的概率——EP 度越大本地命中越少，逼近 1 时可忽略，但 All-to-All 参与方也越多、越怕互联短板。每个 decode 步、每个 MoE 层都来一遍。国产卡的互联是短板：910B 的 HCCS 约 392GB/s、思元590 的 MLU-Link 约 372GB/s（公开汇总口径），只有 NVLink 5（900GB/s）的四成——**EP 通信税在国产卡上翻倍交**。对策按序：① EP 不出节点（8 卡内走 HCCS/MLU-Link，跨节点宁可加副本）；② 大 micro-batch 摊薄通信占比；③ 通信与计算 overlap（DualPipe（双向流水线）类编排，依赖引擎支持，部署前问厂商）。

**EP all-to-all 带宽必须实测，不许查表**：上文的 HCCS/MLU-Link 数值是物理层标称上限，A2A（all-to-all，多卡两两互发通信）有效带宽还受拓扑、消息大小、引擎通信实现影响，实测通常明显低于标称——拿标称值算 EP 通信税，等于又犯一次“裸用经验值”。自测方法：昇腾用 HCCL 通信库自带的 alltoall 压测（hccl_test），寒武纪用厂商对应性能工具；按真实 decode 步的消息大小（≈ B × hidden × 2 字节 × topK）扫“消息大小 × EP 度”矩阵取档，测得的有效带宽作为常数写进锚定记录，换驱动/CANN（昇腾 AI 软件栈）/拓扑任一项都要重测。拿到实测数据之前，EP 通信税一律按“MoE 无卡外推”口径只给量级、不给确数。

**910C 超节点把“EP 不出节点”修订为“EP 不出互联域”**：910C 常以超节点形态交付——整机柜数十至数百颗 NPU 经 UB 总线全互联（公开口径，带宽与 HCCS 同量级，规格以厂商披露为准）——互联域从 8 卡扩大到整柜。EP 度因此可以吃满整个超节点域：大 EP 把每卡专家数摊薄、显存占用大降，这正是超节点跑 R1/V3 的核心收益；但 A2A 一旦跨出互联域落到 RoCE/IB 上，有效带宽掉一个量级，通信税立刻反超收益。规划顺序变为：先确认交付形态的互联域大小 → EP 度按互联域内上限取 → 域外只做副本（DP）。另注意超节点是整机柜采购，单价与供应商锁定风险高，回本测算按 8.3 节口径单独做。

**MLA 是国产卡的天然盟友**：910B 带宽约 1.6TB/s（H20 的 40%），decode 本是带宽游戏，国产卡天然吃亏；但 MLA 把每 token KV 压到 BF16 ≈70KB（每层仅 ~1.1KB，×61 层；FP8 再减半至 35KB），约为标准 GQA 70B（BF16 ≈320KB/token）的 1/5~1/9——对比必须同口径：拿 GQA 整模型的 320KB 去除 MLA 单层的 1.1KB，会得出“1/300”的错位结论。每 token KV 小一个量级，decode 每步的 KV 读取量大减——**带宽短板被 MLA 直接绕开**。选型口诀因此反过来：国产卡优先配 MLA 模型（DeepSeek 系）；GQA 大 KV 模型（Qwen 系 70B 级）在国产卡上 decode 更受伤。KV 槽位墙同理：MLA 下 64GB 的 910B 也能开出上万槽位，KV 墙从决定项退化为校验项（口径同 8.4 算例）。

**寒武纪 思元590 速览**（规格官方未完整公开，以下为公开媒体口径，误差自担）：7nm Chiplet，FP16 ~256 TFLOPS、INT8 512 TOPS、HBM2e 96GB（百科口径）、MLU-Link ~372GB/s、综合约 A100 的 80%（大客户测试口径）、能效比号称超 H20。短板不在纸面算力而在生态：没有 vLLM 级别的成熟开源 serving 栈，生产化要靠厂商交付，排期里给联调留够量。

**昇腾软件栈现状**：vLLM 的昇腾后端走 vllm-ascend 插件，截至本手册 v8.0 处于活跃开发期——算子覆盖、chunked prefill、EP 支持随版本快速变化。在昇腾上锚定前必须锁定“驱动 + CANN + 框架”版本三件套并写进锚定记录，换任何一项都要重锚。

**MLA 在 CANN 上的落地三查**：①查算子——所用 CANN / vllm-ascend / MindIE（昇腾推理引擎）版本是否内置 MLA 融合 attention 算子（支持度随版本快速变化，以厂商 release note 为准）；②查 KV 存储格式——引擎必须把 KV 按压缩潜变量落显存，若展开成标准 MHA 形式，~70KB/token 的优势直接归零，KV 墙按展开后口径重算；③查量化包是否保留 MTP 头（见 9.1）——掉了 MTP 头，accept length 与 decode 速度掉一档。部署示例（锁定“驱动 + CANN + 框架”三件套之后）：

```bash
vllm serve deepseek-ai/DeepSeek-R1 \
  --tensor-parallel-size 8 --enable-expert-parallel \
  --max-model-len 32768 --gpu-memory-utilization 0.92
# 昇腾经 vllm-ascend 插件，CLI 与 vLLM 主线一致；参数名与可用性以所用版本文档为准
```

**国产卡三原则**：① 选卡先看带宽再看算力（decode 是带宽游戏）；② MoE 先问 EP 通信用什么互联、出不出节点；③ MLA 模型优先，GQA 大 KV 模型慎上。
